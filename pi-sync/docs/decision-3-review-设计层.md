## 一、pi-sync 到底在做什么

一句话：**用一个私有 Git 仓库当中转站，让你几台机器上的 Pi 配置保持一致。**

它不是简单的"把文件夹传上去再下下来"。真正麻烦的地方在于三件事：

1. **有些内容不能照搬。** 比如你在 A 机装了个本地开发的插件，路径是 `/home/xyzen/dev/foo`，
   这个声明同步到 B 机就是个死路径。所以需要有东西负责"过滤掉机器专属的内容"。
2. **两台机器可能同时改了同一个文件。** 谁赢？丢掉的那份怎么找回？
3. **同步中途可能崩。** 写了一半的配置比完全没写更糟，所以需要能回滚、能续上。

下面的机制基本都是为了解决这三件事。

## 二、术语表

按理解顺序排列，前面的词不依赖后面的词。

### 位置类

| 术语 | 通俗解释 |
|---|---|
| **agent 目录** | 你本机 Pi 的配置目录，默认 `~/.pi/agent`。**这是同步的目标**，也就是"真正生效的那份配置" |
| **config-repo（配置仓库）** | 本机上的一个 Git 仓库克隆，默认在 `~/.pi/config-repo`。它是**中转站的本地副本** |
| **sync/ 镜像** | 配置仓库里专门存放被同步文件的子目录。你的 `settings.json` 在仓库里的对应物就住在这里 |
| **远端** | GitHub（或别的 Git 服务）上那个私有仓库。几台机器都往这里推、从这里拉 |
| **`.pi-sync/` 目录** | pi-sync 自己的工作目录，存基线、备份、锁、包信任记录。**它自己不参与同步** |

一个容易混淆的点：**"仓库"这个词有两层含义**——本机的克隆和远端。
本文出现"仓库"时默认指**本机克隆**，指远端会明说"远端"。这个区分很重要，
因为三方比较比的是本机克隆，不是远端。

### 状态类

| 术语 | 通俗解释 |
|---|---|
| **基线（baseline）** | **上次同步成功时，每个文件长什么样的存档记录**（存的是内容指纹，不是内容本身）。它是判断"谁改了"的唯一依据 |
| **三方比较** | 拿三个东西对比：基线、本机文件、仓库文件。见第四节，这是整个系统的核心 |
| **B / L / R** | 三方比较的三方缩写：**B**aseline（基线）、**L**ocal（本机）、**R**epo（仓库） |
| **漂移（drift）** | 本机改了但还没推上去的状态。"有漂移"= 你本机有别人还不知道的改动 |
| **指纹（hash）** | 文件内容的数学摘要。内容一样指纹就一样，内容变一个字节指纹就完全不同。用来快速判断"变没变" |

### 动作类

| 术语 | 通俗解释 | 方向 |
|---|---|---|
| **capture（捕获）** | 把本机的改动写进仓库镜像 | 本机 → 仓库 |
| **apply（落地/应用）** | 把仓库的内容写到本机，让它真正生效 | 仓库 → 本机 |
| **pull（拉取）** | 从远端取新内容，然后 apply 到本机 | 远端 → 本机 |
| **push（推送）** | capture 本机改动，提交，推到远端 | 本机 → 远端 |
| **收口** | push 做完之后**必须再跑一次 apply**。原因见第四节 §4.3，这是个反直觉但有意为之的设计 |

### 机制类

| 术语 | 通俗解释 |
|---|---|
| **adapter（适配器）** | 针对特定文件的**翻译器**。比如 `settings.json` 进仓库前要先删掉机器专属字段，这个活儿由 settings adapter 干 |
| **include 清单** | 白名单，决定**哪些文件参与同步**。不在里面的文件 pi-sync 完全不看 |
| **special 声明** | 决定**某个文件由哪个 adapter 处理**。和 include 是两件独立的事 |
| **锁** | 防止两个同步操作同时跑。见第四节 §4.4 |
| **设备恢复分支** | 一个以你机器名命名的 Git 分支，专门用来**存放即将被覆盖的本机提交**，相当于保险箱 |
| **`pendingOperation`（未完成标记）** | 存在磁盘上的一张"便利贴"，写着"上次同步崩在哪一步"。下次同步先读它决定要不要续上 |
| **计划指纹** | 给"同步计划"拍的封条。你看计划时和你点确认时，如果配置变了，封条就不匹配，操作会被拒绝 |

## 三、主要角色的职责

不讲函数怎么写，只讲**谁负责什么**。可以把它当成一张组织架构图。

### 3.1 三个层次

```
   ┌─────────────────────────────────────────┐
   │  扩展层  ——  和 Pi 打交道、和你打交道      │
   │  注册 /pisync 命令、弹对话框、显示状态栏    │
   └─────────────────────────────────────────┘
                      ↓ 调用
   ┌─────────────────────────────────────────┐
   │  编排层  ——  决定"先做什么后做什么"        │
   │  流程调度、加锁、错误恢复                  │
   └─────────────────────────────────────────┘
                      ↓ 调用
   ┌─────────────────────────────────────────┐
   │  核心层  ——  真正干活的                   │
   │  比较文件、读写文件、调 git、装包           │
   └─────────────────────────────────────────┘
```

**一条重要规则：核心层和编排层完全不知道 UI 的存在。**
它们不会弹对话框，只会**返回一个结果说"我需要用户批准"**，然后由扩展层去问你。
这个设计让同步逻辑可以被测试，也是决策 3 有空间可做的前提。

### 3.2 扩展层负责什么

| 角色 | 职责 |
|---|---|
| **命令注册** | 让 `/pisync`、`/pisync status`、`/pisync diff` 出现在 Pi 里，并把参数分派到对应处理器 |
| **对话框驱动** | 所有"问你话"的地方：确认同步计划、批准装包、选择冲突怎么解、问你要不要 reload |
| **状态栏** | 底部那行 "Sync needed" 提示 |
| **autoSync 定时器** | 按配置的间隔在后台偷偷拉取。开会话时启动，关会话时清理 |
| **操作运行器** | 管进度显示、Esc 取消、超时看门狗。它只认识"操作"这个抽象，不懂 git 也不懂同步 |

### 3.3 编排层负责什么

这层最重要的四个角色：

**① 总入口（`run`）** —— 裸 `/pisync` 走的就是它。做七件事，顺序固定：

```
1. 体检     搞清楚现在是什么状态（全新？装过一半？坏了？正常？）
2. 加锁     从这里开始独占，别人进不来
3. 验封条   如果你之前看过计划，检查配置有没有在你犹豫期间变过
4. 洗选择   把你在 UI 里做的选择清洗一遍（防止 UI 传来乱数据）
5. 救场     如果上次崩了留了便利贴，先把上次的活儿收尾
6. 拉取     pull 那一整套
7. 推送     push 那一整套
```

**关键点**：第 6 步没成功（比如需要你批准装包、或者遇到冲突）就**直接停在这里**，
第 7 步根本不会跑。

**② 生命周期判定** —— 只有一个地方判断"当前是什么状态"，四种可能：
全新未初始化 / 初始化中断了 / 状态坏了 / 一切正常。
这个单点判断避免了各处各自猜测导致的不一致。

**③ 计划生成（`plan`）** —— **只读**，不改任何东西。
它算出"如果现在同步，会发生什么"，并给这份计划盖个封条（指纹）。
这是"先预览再执行"的基础。

**④ 冲突转交** —— 把冲突信息（哪个分支、哪些路径、救命分支叫什么）交给扩展层展示。
**pi-sync 自己不解决 Git 冲突**（D9），只提供"交给 agent"和"我自己处理"两条出路，
见第四节 §4.5。

### 3.4 核心层负责什么

| 角色 | 职责 | 一句话 |
|---|---|---|
| **清单与比较** | 枚举文件、算指纹、做三方比较、判定变更类型 | 系统的眼睛 |
| **capture** | 把本机改动写进仓库镜像 | 往外搬 |
| **materialize** | 把仓库内容写到本机，并算出新基线 | 往里搬 |
| **adapter 运行时** | 加载并调度各文件的翻译器 | 翻译调度中心 |
| **settings adapter** | 唯一的内置翻译器，专管 `settings.json` | 见第四节 §4.2 |
| **校验** | apply 前检查：JSON 合法吗？有冲突标记残留吗？包源能跨机吗？ | 质检 |
| **git 封装** | 所有 `git` 命令都从这里出去，统一超时和错误解析 | 对外的嘴 |
| **锁** | 独占控制 | 门卫 |
| **状态存储** | 读写基线和便利贴，用"临时文件+改名"保证不写坏 | 档案室 |
| **备份** | apply 前先备份 | 保险 |
| **包管理** | 调 `pi install` / `pi remove`，管包的审批和信任记录 | 装卸工 |

### 3.5 pull 和 push 的内部步骤

**pull 做的事：**

```
看本机状态
  ↓
本机有改动？→ 有的话先 capture 进仓库并提交
  ↓            （这一步是为了让 rebase 有东西可 rebase）
从远端 fetch
  ↓
能快进就快进，不能就 rebase
  ↓
apply 到本机（含备份、写文件、装包、写基线）
```

**push 做的事：**

```
capture 本机改动
  ↓
校验（JSON 合法？包源便携？）
  ↓
算包变更计划
  ↓
提交
  ↓
fetch + rebase（远端可能有新东西）
  ↓
推共享分支 + 推设备分支
  ↓
apply 收口 ← 就是这一步在写基线
```

**两个反直觉的地方，先记住，第四节解释原因：**

- pull 的第一步居然是 **capture（往外搬）**
- push 的最后一步居然是 **apply（往里搬）**

## 四、四套机制

### 4.1 三方比较：怎么知道谁改了

**核心思路：一个文件在三个地方各有一份，两两对比就能推断出发生了什么。**

- **B（基线）**：上次同步成功时它长什么样
- **L（本机）**：现在你机器上它长什么样
- **R（仓库）**：现在本机的仓库克隆里它长什么样

举例，假设某文件基线指纹是 `abc`：

| 本机 | 仓库 | 结论 | 该怎么办 |
|---|---|---|---|
| `abc` | `abc` | 谁都没动 | 什么都不做 |
| `xyz` | `abc` | 只有你动了 | 推上去（capture） |
| `abc` | `xyz` | 只有别人动了 | 拉下来（apply） |
| `xyz` | `xyz` | 两边都动了，但**改成了一样的** | 不用搬文件，只更新基线 |
| `xyz` | `def` | 两边都动了，**改得不一样** | **冲突** |

"文件不存在"也被当成一种取值参与比较（内部用一个特殊标记表示），
这样"删除"和"新建"就不需要单独的处理逻辑，统一成"内容变了"。很巧妙。

**完整判定表有 14 种情况**，其中 **3 种是冲突**：

- 两边都改了且内容不同
- 本机改了，仓库删了
- 本机删了，仓库改了

**一个需要知道的副作用**：如果某个文件因为权限问题读不出来，
系统会静默把它当作"不存在"，也就是**可能被误判为"你删了它"**。

**另外两点**：
- 文件权限位（chmod）**不参与比较**。只改权限不改内容，系统看不见
- 不在 include 白名单里的文件**根本不进入比较**，不是"被发现然后忽略"，是压根没看

### 4.2 adapter：机器专属内容怎么过滤

问题：`settings.json` 里混着两类东西。

- **该同步的**：主题、默认模型、思考预算……这些你希望几台机器一致
- **不该同步的**：session 目录、追踪 ID、本地插件路径……这些每台机器不一样

**settings adapter 就是那个负责分开这两类的翻译器。** 它在三个方向都工作：

| 方向 | 干什么 |
|---|---|
| **进仓库时** | 只保留白名单里的字段（29 个），并删掉不能跨机的包声明 |
| **出仓库到本机时** | 用仓库的值覆盖白名单字段，**保留你本机白名单外的字段原样**，并把你本机独有的本地插件声明**加回去**（见下方例子） |
| **比较时** | 先按上面的规则过滤一遍再算指纹 |

**"加回去"具体指什么，用一个例子说清楚：**

假设你本机装了一个本地开发中的插件（`file:` 源），`settings.json` 里是：

```json
"packages": ["npm:@xyzensun/pi-sync", "file:~/dev/my-plugin"]
```

**推的时候**，`file:` 指向的路径在别的机器上必然不存在，所以被剥掉，仓库里只存：

```json
"packages": ["npm:@xyzensun/pi-sync"]
```

**拉的时候**，麻烦来了：`packages` 在白名单里，属于"由仓库说了算"的字段，
要被仓库版本覆盖。如果直接覆盖，你本机就只剩 `["npm:@xyzensun/pi-sync"]`
——**pull 一次，本地插件的声明就没了**。

所以 adapter 在覆盖**之前**多做一步：从你本机的旧列表里挑出
**"仓库里没有的、且属于本机私有源"**的条目，覆盖完再**追加回列表末尾**。
最终你本机是：

```json
"packages": ["npm:@xyzensun/pi-sync", "file:~/dev/my-plugin"]
```

共享的部分来自仓库，本机私有的部分原地保留。换台没装过这个插件的机器看：
它 pull 时"本机独有条目"是空的，加回去的也是空，拿到的就是仓库里那份干净列表——
**A 机的本地插件永远不会漏到 B 机，B 机也永远不会缺共享的插件。**

一句话：**pull 只有权动"共享的部分"，你机器上私有的东西它碰不了。**

**第三条特别重要，容易忽略**：如果比较时不过滤，那么"A 机的 sessionDir 和 B 机不一样"
就会被判成差异，**每次同步都会报冲突**。过滤之后，只改机器专属字段的改动会被正确判为"没变化"。

**"能跨机"的包声明**指 `npm:`、`git:`、`https:`、`ssh:` 这几种——它们在任何机器上都能装。
而 `file:`、相对路径、绝对路径、`~/` 开头的，都是本机私有，**永远不进仓库**。

**还有一条保命设计**：adapter 会**强制保证 pi-sync 自己的包声明始终在列表里**。
理由很实际——如果同步把 pi-sync 自己同步没了，那台机器就再也同步不回来了。
三个方向都注入，包括比较方向（否则一边有一边没有，每次比较都判差异）。

**最后一条设计约束值得单独说**：**include 和 special 是完全独立的两件事。**
include 决定"这个文件同不同步"，special 决定"用哪个翻译器"。
不存在"因为文件名叫 settings.json 所以自动启用翻译器"这种隐式逻辑——
`settings.json` 也必须显式声明才走 adapter。

### 4.3 基线什么时候写：那两个反直觉的设计

**规则：基线只在 apply 方向写，而且必须等文件真正落盘成功之后。**

先说为什么这条规则重要。基线是"判断谁改了"的唯一依据。
如果基线写早了（文件还没写成功就更新基线），系统就会**以为同步成功了**，
下次比较时把没同步上的改动当成"没变化"——**改动就凭空消失了**。
所以基线必须是最后一步，且只在真正写文件的那个方向写。

这条规则直接解释了前面两个反直觉的地方：

**为什么 push 的最后要 apply？**
因为 capture（往外搬）**故意不碰基线**。那 push 完之后基线谁来更新？
答案是走一次 apply。此时本机和仓库内容已经一致，
apply 发现"两边一样"，不需要搬任何文件，**只是顺手把基线更新了**。
所以这个 apply 不是多余的，它是**基线的唯一合法写入通道**。

**副作用（对决策 3 很关键）**：既然 push 必然带一次 apply，
而 apply 是"仓库→本机"方向的，那么如果收口时发现远端有新内容，**它会一并落到你本机**。
也就是说 **`/pisync push` 在语义上不可能是纯粹的单向推送**。

**为什么 pull 的第一步要 capture？**
因为要 rebase。rebase 的前提是本机有提交可以 rebase，
所以得先把本机改动 capture 成一个提交，才能把它"重放"到远端最新内容之上。

**另外**：基线是**全量重建的，不是增量修补**。每次成功 apply 都从空白开始，
遍历所有文件重新生成一份完整基线。没被写进去的路径就等于从基线里消失了。
这样不会积累历史垃圾。

**失败时怎么办**：apply 是个事务——先备份，再写文件，再装包，最后写基线。
中间任何一步失败就回滚备份，**只留一张便利贴，绝不动基线**。

### 4.4 锁：谁能同时跑

**最重要的事实：整个系统只有一把锁。**

代码里出现过 10 个不同的操作名（`sync`、`pull`、`push`、`apply`、`init`……），
看起来像是不同的锁，**实际上都是同一个锁文件**，那些名字只是记在锁里的备注，方便诊断。

**推论（对决策 3 直接有用）**：
- pull 和 push **天然互斥，不可能并发**。TUI 不需要处理"一边拉一边推"
- 只读操作（`status`、`diff`、状态栏检查、生成计划）**完全不加锁**，
  所以 **TUI 刷新状态永远不会和同步互相阻塞**

**锁怎么实现的**：靠"排他创建文件"——谁先创建成功谁拿到锁。
锁文件里记着进程号、机器名、开始时间、操作名。

**崩溃了怎么办**：下次有人来抢锁时，会先看锁文件里的进程号**还活着吗**。
死了就认为是残留的僵尸锁，直接删掉重新抢。这个恢复是自动的，不需要你手动清理。
锁文件被写坏（解析不出来）同样会被自动清理。

**但这里有两个隐患**：

- **完全不看时间。** 锁里虽然记了开始时间，但**从来没被读取过**。
  所以一个卡死但进程还在的 pi-sync 会**永久持锁**，只能手工删锁文件
- **进程号可能被复用。** 如果死掉的进程号恰好被系统分配给了别的无关程序，
  探测会认为"进程还活着"，于是永久判定锁有效

**重入问题**：`run` 已经拿着锁了，它内部又要调 pull，pull 也想拿锁——会不会自己把自己锁死？
不会。有一个"我已经拿着锁了"的标志位，内部调用看到这个标志就直接执行，跳过抢锁。
异常时这个标志一定会被复位，不会残留。

**⚠️ 但这个标志位有个漏洞，而且和决策 3 有关：**

这个标志是**挂在实例上的**，而 autoSync 定时器和 `/pisync` 命令**共用同一个实例**。
所以：**如果 autoSync 定时器恰好在你手动同步期间触发，它会看到"已经拿着锁了"这个标志，
于是直通执行，完全绕过锁。**

现有的文档声称"autoSync 与手动同步共用锁，不并发"——
这在**跨进程**（两个 Pi 窗口）时成立，在**同进程**（定时器 vs 你的命令）时**不成立**。

缓解因素：autoSync 有一堆前置检查（工作区脏、有未推送提交、有漂移就跳过），
大概率会自己退出。但时序上确实存在窗口。

**为什么这条和决策 3 有关**：如果 TUI 是常驻界面，你可能长时间停在某个页面上，
**交错窗口会显著变长**。这是 Round 2 必须处理的事。最简单的兜底是加一个
"命令执行中"的标志，autoSync 撞见就跳过。

**还有一张便利贴：`pendingOperation`**

它和锁是两回事，容易搞混：

| | 锁 | 便利贴 |
|---|---|---|
| **作用** | 防止同时跑 | 记录"上次崩在哪" |
| **存在哪** | 锁文件 | 状态文件（磁盘） |
| **进程死了** | **自动失效**（靠进程号探测） | **必须保留**，等下次续上 |

便利贴目前实际只会记一种情况：**apply 时装包失败**。
（还有一种"push 时 rebase 冲突"的取值，但**当前代码里只有读取它的地方，没有任何地方会写它**，
是早期版本迁移留下的遗留值。）

### 4.5 冲突：两个层次，别搞混

这是最容易混乱的部分。**"冲突"这个词在 pi-sync 里指两种完全不同的东西。**

| | 语义层冲突 | Git 层冲突 |
|---|---|---|
| **什么意思** | 三方比较发现两边都改了同一个文件 | git rebase 时产生的那种冲突，文件里有 `<<<<<<<` 标记 |
| **谁发现的** | pi-sync 自己的比较逻辑 | git 报告的 |
| **什么时候** | 搬文件之前 | fetch 之后 rebase 期间 |
| **粒度** | 单个被管理的配置文件 | git 索引里的未合并路径 |

**它们会同时发生**：rebase 冲突处理完之后，还要再做一次三方比较，所以两层都可能报冲突。
系统里有一个专门的转换环节负责把 git 报的路径翻译回 pi-sync 认识的配置文件路径，两层在此汇合。

#### 手动 pull 的策略：远端优先

**冲突时以远端内容覆盖本机，你本机没推上去的改动被丢弃。**
听起来激进，但有兜底（见下）。

这个策略有**三个触发入口**，最终都汇聚到同一个"这些路径用远端内容"的开关，
所以"远端优先"的行为是一致的。

**但它们的可恢复性不一致——这是现有文档没说清楚的地方：**

| 入口 | 什么情况 | 能怎么找回 |
|---|---|---|
| ① | pull 前捕获改动时发现冲突（**你的改动还没提交**） | **只有 apply 前的自动备份** |
| ② | rebase 时 git 报冲突（**你的改动已经提交过**） | 自动备份 **+ 设备恢复分支** |
| ③ | apply 阶段三方比较报冲突 | 自动备份 |

**为什么入口 ① 少一条腿**：设备恢复分支是用来存 git **提交**的。
入口 ① 的改动还没提交，没有提交可存，所以只能靠备份。

**这条直接影响后面 Q3c 的判断。**

#### 设备恢复分支是什么

一个以你机器名 + 一个持久化的设备 ID 命名的远端分支，
形如 `pisync-device/你的机器名-设备ID`。

**它的用法**：当 rebase 冲突、本机提交即将被丢弃时，系统会
先把你的本机提交**完整保存到这个分支并推到远端**，
然后才把主分支重置为远端状态。**所以你的改动没丢，只是不在主线上了。**

为什么要配一个设备 ID 而不只用机器名？因为机器名不保证唯一。
另外系统**从不去扫描远端分支猜测哪个是自己的**——当前设备的分支名是确定可算出来的。

#### push 时冲突：只给两条出路（D9）

和 pull 不同，push 遇到 Git 冲突**不自动决定**，但也**不替你合并**。菜单只有两项：

| 选项 | 会发生什么 |
|---|---|
| 请 agent 解决冲突 | 把一份带约束的合并任务投递给 Pi agent（要求它 fetch、按语义合并、不许整体选边、校验 JSON、不许 force push、完成后提示你重跑 `/pisync`）。pi-sync 投完就撒手，不等结果 |
| 停止 —— 我自己处理 | 打印手动步骤和设备恢复分支名，什么都不做 |

按 Esc 取消等同于第二项——不动是安全默认。设备恢复分支在两种情况下都保留。

**为什么砍掉了"逐个文件选 / 全用本机 / 全用远端"**：
那三项听起来像"合并"，实际只是给 git 的 `ours/theirs` 包了层界面——
它按整个文件二选一，不看内容。真要按语义合并，AI 比它强；真要精确控制，
你自己开编辑器比它透明。夹在中间的能力没有存在价值，反而容易让人误以为
"pi-sync 帮我合并好了"。

这条对 TUI 同样成立：TUI 只展示冲突路径和两条出路，不做合并器。

#### 备份

**什么时候**：apply 事务的第一步，**在任何文件被写之前**。备份失败则整个 apply 中止。

**保留策略：固定 5 份。**
清理发生在**新基线写入磁盘之后**——在那之前的任何失败都还需要旧备份来回滚，
所以不能提前清。清理本身失败不影响这次同步成功。

这和上面"入口 ① 只有备份一条腿"叠在一起看要留意：
超过 5 次同步之前的本机漂移就找不回来了。

## 六、已敲定的决策（Round 1）

### D1 — 命令入口

| 入口 | 行为 |
|---|---|
| `/pisync`（未配置） | **只配置远端仓库，配完就停**。不执行同步、不执行备份 |
| `/pisync`（已配置） | 进入 TUI |
| `/pisync pull` | 智能化拉取（直达，不进 TUI） |
| `/pisync push` | 智能化推送（直达，不进 TUI） |
| `/pisync status` / `diff` | 保持现状（直达） |

**"初始化只配远端、不同步"是本轮的新决定，与现状不同**：
现在的初始化会顺带做首次捕获和一次落地。改动理由是让"配置仓库"和"开始同步"
分成两个你能分别决定的动作，而不是一条命令连做两件事。

### D2 — 两个"智能化"动作 = 现有机制的命名

这是本轮最重要的确认：**"智能化"不是新算法，是给现有流程起的名字。**

| 名称 | 等于什么 | 冲突时怎么办 |
|---|---|---|
| **智能化拉取** | 现有 pull 全流程 | 自动解决：冲突文件用远端内容，本机提交存进设备恢复分支 |
| **智能化推送** | 现有 push 全流程（推共享分支 + 推设备分支） | 弹菜单问你（保留，见 D7） |
| **autoSync** | 智能化拉取 + 永不推送 | 同智能化拉取；但有前置守卫，本机有漂移就整个跳过 |

因为都是既有能力，**同步引擎不需要改动**，工作量集中在入口和界面层。

### D3 — TUI 是两步式菜单

```
TUI
├── 拉取
│   ├── 智能化拉取        （= 现有 pull）
│   └── 以远端覆盖本机     （粗暴档）
└── 推送
    ├── 智能化推送        （= 现有 push）
    └── 以本机覆盖远端     （粗暴档）
```

设计意图（我的理解，如有偏差请纠正）：**第一档给日常用，第二档给"我就是要它听我的"用。**
第二档的价值是可预测性——你不需要理解三方比较也能预期结果。

### D4 — 关于"太黑盒"这个诉求

你提的核心问题是**用户看不见系统在干什么**。记在这里作为决策 3 的验收标准：
每个动作执行前应让你知道**将会发生什么**，执行后应让你知道**实际发生了什么**。
具体形式在 Round 2 定。

---

### D5 — 分工原则：TUI 反黑盒，直达命令要快

这条是本轮定下的**总纲**，后面所有细节都从它推导：

| 入口 | 定位 | 交互风格 |
|---|---|---|
| **TUI** | 解决"太黑盒"（D4） | 该展示的都展示，该问的都问 |
| **`/pisync pull` / `push`** | 解决"TUI 点起来麻烦"，要快 | **可以黑盒**，少问甚至不问 |

所以 D4（反黑盒）**只约束 TUI，不约束直达命令**。两者是互补的两条路，不是同一套标准。

**直达命令的询问清单（已敲定）**：

| 事项 | `/pisync pull` | `/pisync push` |
|---|---|---|
| 计划预览 | 不问 | 不问 |
| 包安装审批 | **不问**（见 Q10 风险敞口） | 不问 |
| 落地会改本机文件 | 不提示 | 不提示 |
| 冲突处理 | 不问（自动远端优先） | **问**（唯一破例，见 D7） |

即两个直达命令**趋近于零询问**，唯一的例外是 push 遇真冲突。

同一件事在 TUI 里则相反：**TUI 保留全部审批与预览**，包括包安装审批。
这不是不一致，而是 D5 的分工本身——两条路服务两种心态。

### D6 — 初始化流程（Q8 + Q9 敲定）

```
/pisync（未配置）
  ↓
问你 Git URL，连上远端
  ↓
问一句"现在拉取远端配置吗？"
  ↓ 是
尝试 pull
  ├── 远端有内容  → 正常拉取落地
  └── 远端是空的  → 按当前机器生成初始清单（全自动，不问）
```

关键点：**"仓库是空的"是在尝试 pull 时才发现的**，不是初始化时先去探测。
发现空仓库就以当前机器为蓝本生成初始清单，这个过程**全自动**。

这样"首台机器"和"后续机器"在流程上是**同一条路**，区别只在 pull 那一步的分支里，
不需要在初始化阶段就分叉。

## 七、Round 2 剩余问题

回答方式：在 **【答】** 处写，或对话里按编号答。认可推荐（➡️）就写"同意"。

> Q8 / Q9 / Q10 / Q11 已敲定，见 D5、D6。本节只剩 Q6、Q7 两题。

### D7 — 冲突是直达命令的唯一破例（Q6 敲定）

`/pisync push` 遇**真冲突**时停下来询问。

这是 D5"直达命令零询问"的**唯一例外**，理由：冲突不是常态（日常 push 不会触发，
不影响"快"）；推送写远端会影响所有其他机器；冲突需要语义判断，
不该由工具静默替用户选边。

### D9 — Git 冲突只给两条出路（后续修订）

D7 定了"要问"，D9 定了"问什么"：**从 5 选项收窄为 2 选项。**

| 保留 | 删除 |
|---|---|
| 请 agent 解决冲突 | 逐个文件选择内容 |
| 停止，由我手动解决 | 所有冲突都使用本机内容 |
| | 冲突使用远端内容 |

**理由**：Git 冲突需要语义判断，pi-sync 提供的"半自动二选一"是能力错位——
既不如 AI 理解内容，也不如用户自己操作透明。既然"交给 agent"才是真语义合并，
保留三个"选边"选项等于把用户往次优解上引。

**适用范围**：`/pisync push` 与 **TUI 一视同仁**——两者在 Git 冲突上用同一套规则
（只展示 + 转交），D5 的快慢分工在此不适用。
TUI 只展示冲突路径、设备恢复分支与两条出路，**不实现合并器**。

**不影响 pull**：pull 的"冲突自动远端优先"是三方比较层（语义层）的裁决，
不是 git 合并器。两个层次的区别见 §4.5。

对照：**`/pisync pull` 遇冲突不问**（自动远端优先）。
不对称是有意的——拉取只影响本机，推送影响所有机器。

### D8 — 两个"覆盖"档 = 整机对齐（Q7 敲定）

TUI 第二档的语义是**整机对齐**，不是"冲突时偏向某一侧"：

| 档位 | 含义 |
|---|---|
| **以远端覆盖本机** | 丢弃本机全部未推送改动，本机变成远端当前的样子 |
| **以本机覆盖远端** | 远端变成本机当前的样子（含删除远端有而本机没有的文件） |

选整机对齐而非"只裁决冲突"的理由：后者**就是现有的智能化拉取**（它已是冲突远端优先），
做成两档没有区分度。整机对齐提供了第一档给不了的东西——
**一个不需要理解三方比较就能预期的确定结果**，正对上"太黑盒"这个诉求。

**⚠️ 这两档是破坏性操作**，必须配套（Round 3 细化）：

1. 执行前**列出将丢失的具体内容**，不能只报数量
2. 明确的二次确认，且**默认选项是取消**
3. 执行前仍走自动备份；"以远端覆盖本机"若本机有已提交内容，仍推设备恢复分支

注意这两档**只存在于 TUI**。直达命令没有对应形态——
想要整机对齐就得进 TUI，这本身也是一道防误触的门槛。

### Q6 — 智能化推送遇到冲突，还问不问？【已定：要问，见 D7】

D2 里有个不对称需要你裁决。**智能化拉取**遇冲突是全自动的（远端优先）。
但**智能化推送**遇冲突，现状是**弹一个 5 选项菜单**
（交给 agent 合并 / 中止 / 逐文件选 / 全用本机 / 全用远端）。

如果"智能化"意味着"不问我、自己搞定"，推送侧这个菜单就和命名矛盾了。

- **A**：**保持弹菜单**。"智能化"仅指"自动处理能自动处理的部分"，真冲突仍然问你
- **B**：**智能化推送也自动决定**，规则取"本机优先"（与拉取的远端优先对称）。
  彻底不问，要精细控制就用第二档
- **C**：**分档**。冲突文件少（如 ≤3）时弹菜单，多了自动本机优先

➡️ **A**，但 D5 让这题变成了**分场景**，需要你确认这个拆法：

| 场景 | 建议 |
|---|---|
| TUI 里选"智能化推送" | **弹菜单**（TUI 本来就该问，符合 D4） |
| `/pisync push` 直达命令 | **也弹菜单** —— 见下方理由 |

直达命令要快（D5），但我认为**冲突是唯一该破例的情况**，理由：

1. **冲突不是常态**。日常 push 没有冲突，菜单根本不会出现，"快"不受影响。
   为了一个罕见路径牺牲安全性不划算
2. **推送写的是远端，会影响所有其他机器**。拉取搞错了只坑自己这一台，
   推送搞错了要去每台机器上收拾
3. **菜单里"交给 agent 合并"是真语义合并**，比任何一侧整体覆盖都好。
   自动化掉是**能力降级**，不是提速

也就是说：`/pisync push` 平时一路不问，**只在真冲突时停下来问一次**。

### Q10 — 直达命令 `/pisync pull` 要不要预览？【已定：不预览】

**背景事实**：现有 pull 内部**收不到你在界面上的选择**，
后果是**远端新增的扩展和包会无提示直接装到你本机**。

**你的决定**：不预览，**包审批也一并省掉**。直达命令就是为了快，可以黑盒（D5）。
反黑盒的责任交给 TUI，不由直达命令承担。

即 `/pisync pull` 全程零询问：拉取、落地、装包、冲突（远端优先）全自动完成。

#### ⚠️ 风险敞口（已知情接受，记录在此以备追溯）

`/pisync pull` 会**静默安装远端 `packages[]` 里声明的包**。
包被安装即意味着**其代码将在本机执行**。因此这条命令的信任模型是：

> **完全信任远端仓库的全部内容，等同于信任在本机执行任意代码。**

前提成立的依据：仓库是作者本人的私有仓库，所有参与同步的机器均为本人所有。

**未被此决定削弱的防线**（这些是机制自带的，不是询问式的）：

| 防线 | 作用 |
|---|---|
| 包源便携性校验 | 只有 `npm:`/`git:`/`https:`/`ssh:` 能进仓库，`file:` 等本机源被剥离 |
| 包信任记录 | 已批准的源记在本机，但**此决定使"首次批准"这一步消失** |
| 安装失败回滚 | 装包失败会回滚已装的包，并回滚本次落地写入的文件 |
| apply 前自动备份 | 文件层面可回退 |
| 插件自排除 | pi-sync 自身永不参与同步 |

**残留的暴露场景**：远端仓库被第三方改动（Git 账号泄露、误 push、
协作者误操作）时，`/pisync pull` 会**无提示地执行对方引入的包**。

**缓解途径（不改本决定的前提下可选）**：

1. **TUI 路径保留完整审批** —— 不确定时走 TUI 而非直达命令（符合 D5 分工）
2. 远端仓库启用分支保护 / 双因素认证，把防线前移到 Git 服务侧
3. 若日后想要一个折中，可加 `/pisync pull --safe` 之类的变体保留审批，
   而不是改变默认行为

**本项决定的边界**：仅适用于 `/pisync pull` 与 `/pisync push` 两个直达命令。
**TUI 内的拉取/推送仍保留包审批**——那是 D4 的范围。

### Q11 — `/pisync push` 会往你本机写文件，接受吗？【已定：接受，不提示】

因为"基线只在落地方向写"这条核心规则（§4.3），push 完成后**必须**
走一次落地收口才能更新基线。而落地是"仓库→本机"方向的，
所以**如果那时远端有新内容，它会一并写到你本机**。

即 `/pisync push` 实际是：捕获 → 提交 → 推送 → **落地收口（可能改你本机文件）**。

**你的决定**：接受，不额外提示。直达命令可以黑盒（D5）。

注：这本来就是现有双向同步的行为，所以这条是"维持现状"，没有额外实现成本。
TUI 里推送时应当把这一步展示出来（那是 D4 的范围）。

## 八、渲染能力查证结果（已完成）

Pi 的界面能力查完了，结论对决策 3 很有利：**不需要从零自绘。**

### 8.1 现成组件够用

pi-tui 导出了一批可直接用的组件，其中三个正好对上我们的需求：

| 组件 | 能做什么 | 对我们的用处 |
|---|---|---|
| **`SelectList`** | 带上下键导航、筛选、滚动的选择列表 | **TUI 主菜单直接用它** |
| **`SettingsList`** | 左标签右当前值的设置列表，**Enter 可循环切换取值，还支持子菜单** | autoSync 开关等配置项 |
| **`Container` / `Box` / `Text`** | 容器、带内边距的盒子、文本行 | 拼版面 |

另有 `Input`（单行输入）、`Editor`（多行编辑）、`Markdown`、`Loader`、`Spacer`、
`TruncatedText`、`Image` 等。

**`SelectList` 自带的能力**（不用自己写）：上下键导航、`setFilter` 筛选、
超出可视区自动滚动并显示滚动提示、`onSelect` / `onCancel` / `onSelectionChange` 三个回调。

**`SettingsList` 更省事**：它的 `SettingItem` 支持 `values?: string[]`
（Enter/Space 循环切值）和 `submenu?`（Enter 进子菜单）。
**D3 那个"拉取 → 智能化/覆盖"的两级菜单，正好是它的 submenu 形态。**

### 8.2 自绘一个组件要写多少

`Component` 接口只要求两个方法：

```
render(width)  → 返回字符串数组（每个元素一行）
invalidate()   → 清缓存
handleInput?   → 可选，处理按键
```

官方示例 `preset.ts` 的做法就是**把 SelectList 包一层**：容器里塞标题 + SelectList + 底部提示，
`handleInput` 直接转发给 SelectList 再调 `tui.requestRender()`。**总共约 40 行。**

所以我们的 TUI 大概也是这个量级——**组装，不是造轮子。**

### 8.3 ⚠️ 一个关键限制：全屏组件和对话框不能嵌套

这条直接影响 TUI 的设计方式，我查了挂载实现确认：

- `custom()` 非浮层模式：**清空编辑器容器**，把你的组件放进去并独占焦点
- `ctx.ui.select()` / `confirm()` / `input()`：**也是清空同一个编辑器容器**，放自己的组件

两者抢的是**同一个位置**。所以在 `custom()` 组件内部调用 `select()` 会
**把你的 TUI 顶掉**，而且对话框关闭时它会把编辑器放回来——你的 TUI 就没了。

**结论：TUI 内部不能复用现有的 `confirm` / `select` 对话框**（包审批、冲突逐文件选择都是这类）。
两条出路：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 状态机式单组件** | TUI 是一个 `custom()` 组件，内部用状态切换不同"页"（菜单页 / 确认页 / 冲突页），全部自己渲染 | 确认和冲突页要自己写，但都是 SelectList 的变体 |
| **B. 先退出再弹窗** | TUI 里选完动作就 `done()` 退出，然后在 TUI 外面走现有对话框流程 | 零新组件，但"退出再回来"的体验割裂 |

➡️ 我倾向 **A**，因为 D4 要求 TUI 是反黑盒的主场，中途被顶掉会破坏连贯性；
而且 `SettingsList` 的 submenu 机制本身就是"页内切换"，有现成范式可依。

另外补一条：`custom()` 支持 `overlay: true` 浮层模式（走 `showOverlay`，不动编辑器容器），
可定位、可设宽高百分比。**浮层模式下能否与对话框共存我没有验证**，
如果 A 方案实现时遇到麻烦，这是一条待探的备选路。

### 8.4 其他确认到的事实

- **按键标识符**齐全：`up` / `down` / `left` / `right` / `enter` / `tab` / `space` /
  `escape` / `pageUp` / `pageDown` / `home` / `end` / `f1`–`f12` / `backspace` / `delete`，
  以及 `ctrl+x`、`ctrl+shift+x` 等组合。方向键和回车都有，导航没问题
- **重绘**由组件自己触发：状态变了就调 `tui.requestRender()`。
  `invalidate()` 是框架在主题切换等场合调用的，用来清组件内部缓存
- **非 TUI 模式下 `custom()` 直接返回 `undefined`**（不是报错）。
  所以 `-p` 等模式必须先判 `ctx.mode === "tui"`，否则 TUI 那条路会静默什么都不做
- 官方示例里有 14 个用了 `custom()`，其中 `preset.ts`（SelectList 菜单）和
  `questionnaire.ts`（多步骤状态机 + 内嵌 Editor）是最贴近我们需求的两个范本

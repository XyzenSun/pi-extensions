## 一、背景与目标

### 1.1 要解决的问题

同步算法本身完善，但**对使用者是黑盒**：`/pisync` 一条命令包办初始化、拉取、推送，
中途弹若干对话框，用户无法预先知道会发生什么，也无法只做半程。

### 1.2 两个诉求是冲突的

| 诉求 | 想要什么 |
|---|---|
| 看清楚 | 每步都告诉我将发生什么、实际发生了什么 |
| 快 | 别问那么多，我知道我在干什么 |

**本设计不折中，而是分给两条路**：TUI 负责看清楚，直达命令负责快。

### 1.3 分工原则（核心设计约束）

| 入口 | 定位 | 交互风格 |
|---|---|---|
| **TUI** | 反黑盒 | 该展示的都展示，该问的都问 |
| **`/pisync pull` / `push`** | 快速精准操作 | 趋近零询问 |

## 二、命令入口总览

| 命令 | 行为 | 状态 |
|---|---|---|
| `/pisync`（未配置） | 只配置远端仓库，配完停下询问是否首次拉取 | 待实现（D6） |
| `/pisync`（已配置） | 进入 TUI | **已实现** |
| `/pisync pull` | 智能化拉取 | **v0.2.0 实现** |
| `/pisync push` | 智能化推送 | **v0.2.0 实现** |
| `/pisync status` | 详细状态文本 | 已有，不变 |
| `/pisync diff` | 差异全屏查看 | 已有，不变 |

### 2.1 术语：什么是"智能化"

**"智能化"不是新算法，是给现有流程起的名字。** 这条很重要，它意味着零引擎改动。

| 名称 | 等于什么 |
|---|---|
| 智能化拉取 | 现有 pull 全流程：捕获本机改动 → fetch → 快进/rebase → 落地（含备份、写文件、装包、写基线） |
| 智能化推送 | 现有 push 全流程：捕获 → 校验 → 提交 → fetch/rebase → 推共享分支 + 推设备分支 → 落地收口 |
| autoSync | 智能化拉取 + 永不推送 + 前置守卫（本机有漂移就整个跳过） |

## 三、v0.2.0 范围：直达命令

### 3.1 `/pisync pull`

**语义**：智能化拉取。**零询问**。

| 事项 | 行为 |
|---|---|
| 计划预览 | 不展示 |
| 包安装审批 | **不询问，自动批准**（见 3.3 风险） |
| 扩展逐项选择 | 不询问（现有 pull 本就不触发该门禁） |
| 冲突 | 不询问，自动远端优先 |
| 落地结果 | 执行后汇报实际改了什么 |
| reload 提示 | 保留（配置变了需要 reload 才生效，这是必要信息而非审批） |

**不推共享分支**。注意措辞：rebase 冲突时**会**推设备恢复分支，那是保命写入，保留。
所以 pull 不是字面意义的"零远端写入"。

**前置检查**：先判生命周期，未初始化时给出可操作的提示而非抛错。

### 3.2 `/pisync push`

**语义**：智能化推送。**除冲突外零询问**。

| 事项 | 行为 |
|---|---|
| 计划预览 | 不展示 |
| 包安装审批 | 不询问，自动批准 |
| **Git 冲突** | **询问**（唯一破例），只给两个选项：交给 agent / 我自己处理（见 3.2.1） |
| 落地收口改本机文件 | 不额外提示 |
| reload 提示 | 保留 |

**为什么冲突要破例**（与"零询问"的唯一例外）：

1. 冲突不是常态，日常 push 不触发，不影响"快"
2. 推送写远端，**影响所有其他机器**；拉取只影响本机，风险不对称
3. 冲突需要语义判断，不该由工具静默替用户选边

### 3.2.1 Git 冲突只给两条出路（D9）

**pi-sync 不提供 Git 冲突合并器。** 它既不如 AI 理解内容语义，
也不如用户自己操作透明——介于两者之间的"半自动二选一"属能力错位。

| 选项 | 行为 |
|---|---|
| 请 agent 解决冲突 | 向 Pi agent 投递合并任务（fetch、把设备分支合并进共享分支、解冲突、校验 JSON、commit+push、完成后提示重跑 `/pisync`）。pi-sync **不等待其完成** |
| 停止，由我手动解决 | 显示手动处理步骤与设备恢复分支名（`origin/pisync-device/<机器名>-<设备ID>`），不做任何自动处理 |

**删除的三个旧选项**（v0.2.0 仍在，待清理）：

| 被删选项 | 删除理由 |
|---|---|
| 逐个文件选择内容 | 替用户逐文件二选一，非语义合并，只是给 `ours/theirs` 包了层 UI |
| 所有冲突都使用本机内容 | 同上的批量版；且易与 §4.2 的"以本机覆盖远端"混淆——它只作用于**当前 git 冲突路径**，不是整机对齐 |
| 冲突使用远端内容 | 同上 |

**不影响 pull**：`/pisync pull` 的"冲突自动远端优先"是三方比较层的裁决（D7），
不是 git 合并器，保持不变。

### 3.3 风险敞口（已知情接受）

两个直达命令**静默安装远端 `packages[]` 声明的包**，包被安装即意味着**其代码在本机执行**。
信任模型是：

> 完全信任远端仓库的全部内容，等同于信任在本机执行任意代码。

前提成立依据：仓库为作者本人私有仓库，所有参与同步的机器均本人所有。

**未被削弱的防线**（机制自带，非询问式）：

| 防线 | 作用 |
|---|---|
| 包源便携性校验 | 只有 `npm:`/`git:`/`https:`/`ssh:` 能进仓库 |
| 安装失败回滚 | 回滚已装的包 + 回滚本次落地写入的文件 |
| 落地前自动备份 | 文件层面可回退，保留最近 5 份 |
| 插件自排除 | pi-sync 自身永不参与同步 |

**残留暴露场景**：远端仓库被第三方改动（账号泄露、误 push）时，直达命令会无提示执行对方引入的包。

**缓解**：不确定时走 TUI（保留完整审批）；远端启用分支保护 / 2FA。

### 3.4 非 TUI 模式行为

`ctx.hasUI === false`（`-p`、json 模式）时，两个直达命令**仍应可用**——
它们本就零询问，不依赖对话框。仅 reload 确认需要降级为通知。

## 四、TUI 范围（后续版本）

### 4.1 菜单结构

```
/pisync（已配置）
└── TUI
    ├── 状态总览（常驻顶部）
    ├── 拉取
    │   ├── 智能化拉取        = 现有 pull，但保留全部审批与预览
    │   └── 以远端覆盖本机     整机对齐（破坏性）
    ├── 推送
    │   ├── 智能化推送        = 现有 push，保留全部审批与预览
    │   └── 以本机覆盖远端     整机对齐（破坏性）
    ├── 查看差异
    └── 设置（autoSync 开关等）
```

**TUI 与直达命令的关键差异：TUI 保留包审批与计划预览，直达命令不保留。**
同一个能力，两种交互契约。

### 4.2 两个"覆盖"档 = 整机对齐

| 档位 | 语义 |
|---|---|
| 以远端覆盖本机 | 丢弃本机全部未推送改动，本机变成远端当前的样子 |
| 以本机覆盖远端 | 远端变成本机当前的样子（含删除远端有而本机没有的文件） |

**为什么是整机对齐而非"冲突时偏向某侧"**：后者就是现有的智能化拉取（已是冲突远端优先），
做成两档没区分度。整机对齐提供的是**不需要理解三方比较就能预期的确定结果**。

**破坏性操作的强制要求**：

1. 执行前**列出将丢失的具体路径**，不能只报数量
2. 二次确认，**默认选项是取消**
3. 仍走落地前自动备份；本机有已提交内容时仍推设备恢复分支
4. **只存在于 TUI**，无直达命令形态——进 TUI 本身是一道防误触门槛
5. 若过程中遇到 **Git 冲突**，同样只给 §4.2.1 的两条出路，
   **不得退化为逐文件选边**

### 4.2.1 TUI 不实现 Git 冲突解决器（D9）

TUI 遇到 Git 冲突时**只做展示与转交**：

| TUI 应该做 | TUI 不应该做 |
|---|---|
| 显示发生了冲突 | 逐文件选择 ours/theirs |
| 显示冲突路径清单 | 自动 checkout 某一侧 |
| 显示设备恢复分支名 | 自动提交解决结果 |
| 提供"交给 agent 解决" | 代替用户完成 git merge |
| 提供"我自己处理" + 手动步骤 | |

这一条与 §3.2.1 完全一致——**直达命令与 TUI 在 Git 冲突上采用同一套规则**。
D5 的分工（TUI 反黑盒、直达命令要快）在此不适用：
两者都只是"展示 + 转交"，没有快慢之分。

注意区分两个层次（详见 `decision-3-review-设计层.md` §4.5）：

- **Git 层冲突** → 本节规则：只转交，不合并
- **语义层冲突**（三方比较判出的 both_modified 等）→ 仍由引擎按既定策略裁决
  （pull 远端优先、整机对齐档按所选方向），这不是"手动合并器"

### 4.3 渲染方案

**结论：组装 pi-tui 现成组件，不自绘引擎。**

可用组件：

| 组件 | 用途 |
|---|---|
| `SelectList` | 主菜单。自带上下键导航、筛选、滚动、`onSelect`/`onCancel` |
| `SettingsList` | 设置项。`values[]` 支持 Enter 循环切值，`submenu` 支持二级菜单 |
| `Container` / `Box` / `Text` | 版面拼装 |

`Component` 接口只要求 `render(width)` 返回字符串数组 + `invalidate()`，`handleInput` 可选。
官方 `preset.ts` 用 SelectList 做菜单约 40 行，`questionnaire.ts` 是多步骤状态机范本。

**⚠️ 硬限制：全屏组件与对话框不能嵌套。**
`custom()` 非浮层模式与 `select()`/`confirm()`/`input()` 抢占**同一个编辑器容器**。
在 TUI 内调对话框会把 TUI 顶掉，且对话框关闭后会恢复编辑器——TUI 消失。

**因此 TUI 采用状态机式单组件**：一个 `custom()` 组件内部切页
（菜单页 / 确认页 / 冲突提示页 / 结果页），各页自行渲染（均为 SelectList 变体）。

注意"冲突提示页"按 §4.2.1 只做**展示 + 两条出路**，不是合并器——
所以它是一个静态清单加两项选择，实现量很小。

备选路：`custom({ overlay: true })` 走独立 overlay 通道不动编辑器容器，
**但浮层与对话框能否共存未验证**，仅在状态机方案遇阻时探索。

**非 TUI 模式**：`custom()` 返回 `undefined` 而非报错，故必须显式判 `ctx.mode === "tui"`，
否则 TUI 路径静默失效。

### 4.4 初始化流程（改动现状）

```
/pisync（未配置）
  ↓
问 Git URL → 连上远端 → 【停】
  ↓
问"现在拉取远端配置吗？"
  ↓ 是
尝试 pull
  ├── 远端有内容 → 正常拉取落地
  └── 远端是空的 → 按当前机器生成初始清单（全自动，仅展示不询问）
```

**与现状的差异**：现在的初始化会顺带做首次捕获和一次落地。
改为"只配远端就停"，把"配置仓库"和"开始同步"拆成两个可分别决定的动作。

"发现远端为空"是在**尝试 pull 时**才判定，不在初始化阶段预先探测——
这让首台机器与后续机器走同一条路径，分支只在 pull 内部。

### 5.4 实现说明

**分层**：状态机 / 渲染 / 按键 / 组装四层拆开，前三层是纯函数，
组装层的动作经接口注入。因此全部可脱离终端单测（`test/tui-*.test.ts`）。

**三件事在面板关闭后才做**——它们要用 `ctx.ui` 对话框或 `pi.sendUserMessage`，
在 `custom()` 内部调用会顶掉 TUI（§4.3）：投递 agent 合并任务、展示差异、
询问 reload。状态机以 `TuiExitIntent` 把意图交还扩展层。

**整机对齐的删除语义**（决策见 `v0.2.0.md` D10）：**不受 `config.delete` 约束**。
那个开关管的是"删除要不要跨机传播"，而整机对齐是用户显式要求的一次性动作，
确认页已逐条列出待删路径。常规 apply 仍尊重 `delete: "none"`。

**`overwriteFromLocal` 的执行顺序**：fetch → 快进 → 镜像覆盖 → push。
先取远端是必需的：跳过它会让随后的 push 因落后于远端而 rebase，
撞上镜像改动产生 Git 冲突——用户明明选了"以本机覆盖远端"却收到冲突提示。

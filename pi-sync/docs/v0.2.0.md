## 决策 1：界面与代码全量中文化

**背景**：此插件仅供作者本人使用，母语为中文，因此所有面向使用者的文字以及代码内的表达均统一改为中文。

### 已确认规则

**范围（全量）**

所有以下内容改为中文：
- TUI 菜单项、confirm/input/select 提示语、操作结果通知（`ctx.ui.notify` 等）
- 运行时错误消息（`throw new Error(...)`、`return { message: "..." }` 等）
- `onProgress` 进度消息
- 内部日志（`console.log`、`console.error` 等）
- 源码注释（`//`、`/** */`）

不改的内容：
- 测试文件的 `describe` / `it` 描述字符串（维持英文）
- 代码标识符（变量名、函数名、类名、枚举值）
- 技术术语插值（URL、文件路径、命令名、数量等动态值保留原文，只翻译包裹文字）
- **解析外部命令（git / npm / pi CLI）输出的匹配串一律保留英文**

最后一条是硬约束，不是风格偏好：这些字符串匹配的是外部程序自己输出的英文，
翻译后匹配恒假，功能会静默失效且不抛任何错误。已确认必须保留的位置：

| 位置 | 匹配串 | 作用 |
|---|---|---|
| `src/system/git.ts:393-395` | `"UU "` `"AA "` `"DD "` | git status 冲突状态码 |
| `src/system/git.ts:566-567` | `"Already up to date"` `"Already up-to-date"` | git merge 输出 |
| `src/system/git.ts:636-637` | `"Current branch"` `"is up to date"` | git pull 输出 |
| `src/system/git.ts` 其他 | `fatal:` 正则、`/CONFLICT/i`、`nothing to commit` | 认证失败与冲突判定 |

同理，**既是显示文本又充当匹配键的字符串**，两端必须同步修改：

- `index.ts` 中 `choice === "取消同步"` 等选项比较：标签与比较值须逐字一致，否则菜单全部落入取消分支
- `index.ts` 的 `MANUAL_MERGE_HEADING` 须与 `commands.ts` 产出该行的文案逐字一致（已在代码中加注说明）
- `commands.ts` 的 `autoSyncOnce` 靠消息子串判断"是否已有同步在跑"，消息与判定须一起改

示例：
```
// 改前
onProgress?.(`Cloning ${gitUrl}...`);
throw new Error("No config repo found. Run /pisync to set up.");

// 改后
onProgress?.(`正在克隆 ${gitUrl}...`);
throw new Error("找不到配置仓库，请先运行 /pisync 完成初始化。");
```

**Git commit 消息格式**

保留 Conventional Commits 前缀，正文改为中文：
```
feat: 添加自动同步功能
fix: 修复 file: 路径被误判为非便携包源的问题
chore: 全量中文化界面文字与代码注释
```

**执行方式**

一次专门的全量中文化 pass，作为独立 commit 完成，之后所有新代码直接用中文书写。

**涉及的主要字符串位置（来自代码扫描）**

## 决策 2：便携性校验 adapter 化

**背景**：`validate.ts:203` 与 `materialize.ts:230` 两处按文件名硬编码 `relPath === "settings.json"` 触发便携性校验，与 `special` 声明无关。这与已确认的 A2 决策（只有 `special` 声明的文件才做特殊处理）冲突，具体后果：

- `settings.json` 仅在 `include` 中（字节直传）时仍被校验
- 用户用 `./my-adapter.js` 接管 `settings.json` 时，仍按内置规则校验，用户 adapter 说了不算
- 其他路径（如 `config/other.json`）声明用 `settings` adapter 时反而不被校验

讽刺的是 `materialize.ts:241`——硬编码下方第 11 行——用的正是正确写法 `hasAdapter(config, relPath)`。同一函数内两套分派规则并存。

此外两处判定标准不一致：`validate.ts:80/88-95` 判 error 要求 `/` 或 `~/` 开头、判 warning 要求 `.`/`/`/`~` 开头，**`file:` 前缀两者都不满足，完全漏检**；而 `settings-adapter.ts` 的 `isPortablePackageSource()` 明确判其不可便携。

**重要前提**：包源的强制拦截不在 `validate.ts`。`packages.ts` 的 `parsePackageDeclarations()` 解析远程 settings 时不带 `skipInvalid`，遇 `file:` 直接抛错并被 `push-flow.ts:318` 转为 blocked。因此 `validate.ts` 那段是冗余的、更弱的、分派还错的副本——删除它不会削弱安全性。

### 已确认规则

**校验归入 adapter**

- `FileAdapter` 增加第四个可选方法（校验方向），与 `toRepository`/`toLocal`/`normalizeForComparison` 同构，未实现即不校验
- `file-adapters.ts` 增加对应包装函数，语义与现有三个一致
- `validate.ts` 与 `materialize.ts` 的两处文件名硬编码改为按 `special` 分派
- 内置 `settings` adapter 的校验**只做包源便携性检查**，复用 `isPortablePackageSource()`，消除两套标准

**删除的检查项**

| 原检查项 | 删除理由 |
|---|---|
| `externalEditor` 为绝对路径 | 该字段不在白名单内，走 adapter 时进不了仓库 |
| 内容含 `/home/` 或 `/Users/` | 启发式过宽，`AGENTS.md` 等正常内容会被误报 |
| repo settings 缺少 pi-sync 自身声明 | 改为强制注入（见下），无需再警告 |

**强制注入自身包声明**

`settings` adapter 保证 `packages[]` 中始终含 `npm:@xyzensun/pi-sync`，防止同步插件把自己弄没导致再也同步不回来。

- 三个方向**全部注入**：`toRepository`（写入仓库前）、`toLocal`（写入本机前）、`normalizeForComparison`（比较前）
- 规则表述为一句无条件的话："该声明永远在 `packages[]` 里"，不分方向
- `normalizeForComparison` 必须同步注入，否则一侧有一侧无会导致每次比较都判为差异
- 包名字面量现散落在 `validate.ts`（2 处）与 `packages.ts:554`，抽为共享常量
- 已知代价：使用目录扩展形态（`extensions/pi-sync/`，不走 `pi install`）时，本机 settings 会被注入 npm 声明，可能导致 npm 版与目录版并存。用户全部机器均以 `pi install` 安装，接受此代价

### 受影响位置

| 文件 | 改动 |
|---|---|
| `src/sync/adapter-runtime.ts` | `FileAdapter` 增加校验方法；定义自身包名常量 |
| `src/sync/file-adapters.ts` | 增加校验方向的包装函数 |
| `src/sync/settings-adapter.ts` | 实现校验方法（仅包源检查）；三个方向注入自身包声明 |
| `src/sync/validate.ts` | 删除 `validateSettingsPortability` 与文件名硬编码分支 |
| `src/sync/materialize.ts` | 删除文件名硬编码分支，改用 adapter 分派 |
| `src/system/packages.ts` | `isBuiltInTrustedSource` 改用共享常量 |
| `test/validate.test.ts`、`test/adapter.test.ts` | 对应调整 |

### 关联待办

插件加载完整性检查应在同步完成后检查**本机实际状态**（`extensions/` 目录或已安装包），而非检查仓库 JSON 字段——后者只是间接信号且易误报。本次不实现。

## 决策 3：TUI 与命令入口

完整需求见 `docs/tui-prd.md`；机制查证与访谈过程见 `decision-3-review.md` / `decision-3-review-设计层.md`（一次性评审材料，TUI 落地后可删除）。

### 已定稿的决策（访谈 Round 1/2 敲定）

| # | 决策 |
|---|---|
| D1 | `/pisync` 未配置 → 只配远端仓库、配完询问是否立即拉取；已配置 → 进 TUI。`pull`/`push`/`status`/`diff` 为直达命令 |
| D2 | "智能化拉取/推送" = 给现有 pull/push 流程命名，**同步引擎零改动** |
| D3 | TUI 为两级菜单：拉取{智能化, 以远端覆盖本机}、推送{智能化, 以本机覆盖远端} |
| D4 | 反黑盒是 TUI 的验收标准：执行前知道将发生什么、执行后知道实际发生了什么 |
| D5 | **分工总纲**：TUI 反黑盒（保留审批与预览），直达命令要快（趋近零询问） |
| D6 | 初始化"只配远端"；尝试 pull 时发现远端为空则按当前机器生成初始清单（全自动） |
| D7 | 冲突是直达命令的唯一破例：push 遇冲突弹现有菜单，pull 自动远端优先 |
| D8 | 两个"覆盖"档 = 整机对齐（丢弃一侧全部未推送改动），仅存在于 TUI，配二次确认 |
| D9 | **Git 冲突不由 pi-sync 解决**：只提供"交给 agent"与"我自己处理"两条出路，删除逐文件 ours/theirs 与整体选边的手动合并器 |

### D9 的完整表述与理由

**Git 层冲突（rebase/merge 产生的 CONFLICT）需要语义判断，pi-sync 不该提供介于两者之间的"半自动二选一"。**
它既不如 AI 理解内容语义，也不如用户自己操作透明，属于能力错位。

保留的两条出路：

| 选项 | 行为 |
|---|---|
| 请 agent 解决冲突 | 向 Pi agent 投递合并任务（fetch、把设备分支合并进共享分支、解冲突、校验 JSON、commit+push、完成后提示重跑 `/pisync`）。pi-sync 不等待其完成 |
| 停止，由我手动解决 | 显示手动处理步骤与设备恢复分支名，不做任何自动处理 |

删除的三个选项：

| 被删选项 | 删除理由 |
|---|---|
| 逐个文件选择内容 | pi-sync 替用户逐文件二选一，非语义合并，只是把 `ours/theirs` 包了层 UI |
| 所有冲突都使用本机内容 | 同上的批量版；且易与 D8 的"以本机覆盖远端"混淆——它只作用于**当前 git 冲突路径**，不是整机对齐 |
| 冲突使用远端内容 | 同上 |

**适用范围**：

- ✅ `/pisync push` 的冲突交互
- ✅ TUI 内的 Git 冲突交互（TUI 只展示冲突路径、设备恢复分支与两条出路，**不实现合并器**）
- ✅ TUI 整机对齐档遇到 git 冲突时，同样只给这两条出路，不得退化为逐文件选边
- ❌ **不影响 `/pisync pull`**：pull 的"冲突自动远端优先"是已定的单向策略（D7），
  属于三方比较层的裁决，不是 git 合并器

**与 D7 的关系**：D7 说"冲突是直达命令的唯一破例（push 遇冲突要问）"仍然成立，
D9 只是把"问什么"从 5 选项收窄为 2 选项。

### 直达命令的风险记录（已知情接受）

两个直达命令**自动批准并安装远端 `packages[]` 的包**，信任模型等同"完全信任远端仓库内容 = 信任在本机执行任意代码"。前提：私有仓库 + 全部机器为本人所有。机制防线不变（便携源过滤、安装失败回滚、落地前备份保留 5 份、插件自排除），但"首次审批"交互消失，**TUI 内保留完整审批**作为不确定时的替代路径。

### D10：整机对齐的删除语义不受 `config.delete` 约束

**决策**：TUI 两个"覆盖"档执行删除时，**不看 `config.delete`，要删就真删**。

| 场景 | 行为 |
|---|---|
| 整机对齐（TUI 覆盖档） | 一律删到两边完全一致，`delete: "none"` 也不例外 |
| 常规 pull / push / apply | 不变，仍尊重 `delete: "none"` |

**理由**：`config.delete` 管的是"删除要不要**跨机传播**"——那是常态同步的策略。
而整机对齐是用户在 TUI 里**显式要求的一次性动作**，语义就是"完全复刻另一侧"。
若受该开关约束，结果会变成"内容盖上去了但多余文件还在"，既不是对齐、也无法预期，
违背 `tui-prd.md` §4.2 "不需要理解三方比较就能预期的确定结果"这一立意。

**安全边界未削弱**：确认页逐条列出将删除的具体路径且默认停在取消（§4.2 要求 1、2），
落地前仍自动备份，白名单外的文件依然永不参与。
